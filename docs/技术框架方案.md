# Win7 AI 教学编辑器 —— 技术框架方案

> 版本：v1.1（决策已锁定）| 支持范围：**Windows 7 SP1 ~ Windows 10**，32/64 位
> 分发形态：免安装 zip | 打包方式：**仅 GitHub Actions**

---

## 1. 项目定位

面向教学场景的 AI 代码编辑器，运行环境以学校机房的老旧机器（Windows 7）为下限。
目标用户是零基础学生和授课老师，不是专业开发者，功能优先级：

1. **能跑起来** —— 在老机器上稳定启动，这是一切的前提
2. **能看懂** —— 编辑 + 实时预览 + AI 讲解，降低入门门槛
3. **能练** —— 分步任务、自动检查点（后续阶段）

不需要终端、调试器、Git 集成、插件市场。这些能力的开发成本和兼容风险都极高，且与教学无关。

## 2. 已确认决策

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 系统与架构覆盖 | Win7 SP1 / Win10，各支持 32 位与 64 位 |
| 2 | Win11 | **不支持**（不纳入测试，遇到问题不修复）|
| 3 | AI 接入 | OpenAI 兼容协议，走中转站 |
| 4 | 代码执行沙箱 | 暂不考虑，后续再评估 |
| 5 | 分发形态 | 免安装版（zip）|
| 6 | 打包方式 | **仅 GitHub Actions**，开发环境不打包 |

### 一个重要的范围澄清

「Win7 32/64 + Win10 32/64」看起来是 4 个版本，**实际只需要 2 个产物**。

原因：**Windows 版本不是打包维度，架构才是。** Electron 22 是向下兼容的，同一份 x64 包在 Win7 SP1 / Win8 / Win10 上都能运行。操作系统之间的差异用**运行时自适应**解决（见 §5.2），不需要为每个系统单独构建。

另外两点事实：

- **Windows 11 没有 32 位版本**（只有 x64 和 ARM64），不存在「win11 32」这个组合
- **非 SP1 的 Windows 7 无法启动 Electron 22**，所以 x64 包的实际门槛是「Win7 SP1 及以上」

## 3. 硬约束：Electron 版本锁死在 22.x

| 事实 | 影响 |
|---|---|
| **Electron 22.x 是最后一个支持 Windows 7/8/8.1 的大版本**，23 起要求 Windows 10 1809+ | 版本钉在 **22.3.27**（该线最后一个补丁）|
| Electron 22 内置 **Chromium 108 / Node 16.17.1 / V8 10.8** | 渲染进程上限 = Chrome 108；主进程上限 = Node 16 |
| Chromium 对 Win7 的官方支持止于 109 | 换内核也无法突破，不存在「魔改更优解」|

### 为什么不是 Tauri / NW.js / 原生方案

- **Tauri**：依赖 WebView2（Win10+ 才有）。Tauri v1 在 Win7 上退化到 MSHTML/EdgeHTML，无法承载 Monaco —— 直接出局
- **NW.js**：Win7 支持状况更差，社区与维护度不如 Electron
- **WPF / WinForms**：要自己实现代码编辑器（高亮、缩进、补全），成本高一个数量级，AI 流式渲染体验也差

### 禁止清单（硬红线）

违反任一条，都会在 Win7 上直接出问题：

| 禁止项 | 原因 |
|---|---|
| 升级 electron 超过 22.x | 直接不支持 Win7 |
| 引入原生模块（node-pty / better-sqlite3 / sharp / keytar）| 需匹配 Electron ABI 110，预编译包不可用 |
| 主进程使用全局 `fetch` / `structuredClone` | Node 16 没有，运行时报错 |
| 渲染进程使用 Chrome 109+ 的语法或 CSS | 白屏或样式错乱 |
| 渲染进程直接请求外部 API | CORS + 密钥泄露 + 绕过系统代理 |
| 依赖 WebView2 / Win10 通知 API / 托盘透明窗口 | Win7 不存在或行为不一致 |
| 启用 electron-updater | Win7 需 KB4474419 才能验 SHA-2 签名 |

## 4. 技术栈清单

### 4.1 运行时（不可变）

```
Electron 22.3.27
  ├── Chromium 108.0.5359.215   → 渲染进程上限
  ├── Node 16.17.1              → 主进程上限
  └── V8 10.8
```

### 4.2 开发与构建

| 层 | 选型 | 版本 | 理由 |
|---|---|---|---|
| 构建编排 | electron-vite | 2.3.0 | 主/预加载/渲染三份独立配置，一套命令搞定 |
| 打包 | electron-builder | 24.13.3 | zip 目标跨平台稳定，配置即代码 |
| 语言 | TypeScript | 5.6.3 | 跨进程契约类型安全 |
| 前端 | React | 18.3.1 | 生态成熟，不用实验性特性 |
| 状态 | zustand | 4.5.5 | 纯 JS 无依赖 |
| 编辑器 | Monaco Editor | 0.44.0 | VS Code 同源，自带 Python/Java/C++/HTML 高亮 |
| 样式 | 原生 CSS + 变量 | — | 不引 UI 框架，减少体积与兼容面 |
| CI | GitHub Actions | windows-2022 | 唯一打包入口 |

**Monaco 版本不追新**：0.47+ 对新浏览器特性有要求。0.44 是验证过能在 Chromium 108 上稳定运行的版本，升级必须做真机回归。

### 4.3 构建目标锁定（关键护栏）

```ts
main:     { build: { target: 'node16'    } }   // 主进程
preload:  { build: { target: 'node16'    } }   // 预加载（electron-vite 强制 node 目标）
renderer: { build: { target: 'chrome108' } }   // 渲染进程
```

这里有个容易踩的坑：**预加载层不能用 `chrome108` 目标**。electron-vite 会直接报错，
因为预加载脚本跑在 Node 上下文（不是普通渲染页面）。所以它跟主进程一样锁 `node16`，
但预加载里不能写任何文件读写逻辑 —— 它只做 `contextBridge` 桥接。

价值在于：**esbuild 遇到超出目标环境的语法会直接构建报错**，而不是默默打出一个在 Win7 上白屏的包。兼容性从「靠人记得」变成「编译不过」。

### 4.4 第二道护栏：Node 16 API 静态检查

目标锁定能拦住**语法**，拦不住 **API**。例如 `fetch()` 是合法语法，但 Node 16 没有它。

而且这里有个坑：构建工具链本身要求 `@types/node >= 18`（vite 的 peer 依赖），
所以**类型层面守不住这条边界** —— 用 Node 20 的类型写代码，编译能过，到了 Win7 上运行才报错。

因此额外加一道静态扫描（`scripts/check-node16-api.mjs`，已接入 `npm run build`）：

| 被拦住的 API | 首次可用版本 |
|---|---|
| `fetch()` | Node 18 |
| `structuredClone()` | Node 17 |
| `Array.prototype.findLast` | Node 18 |
| `AbortSignal.timeout()` | Node 17.3 |
| `fs.statfs()` | Node 18.15 |
| `FormData` / `Response` / `Headers` 全局 | Node 18 |
| `Object.groupBy()` | Node 21 |

只扫描 `src/main` 与 `src/shared`（跑在 Node 16 环境）；`src/renderer` 跑在 Chromium 108，不受此限。

**两道护栏的分工**：`chrome108` / `node16` 拦语法，静态检查拦 API。

## 5. 支持范围与运行时自适应

### 5.1 支持矩阵

| 系统 | 64 位 | 32 位 | 支持等级 |
|---|---|---|---|
| Windows 7 **SP1**（6.1.7601）| x64 包 | ia32 包 | **承诺支持** |
| Windows 10 | x64 包 | ia32 包 | **承诺支持** |
| Windows 8 / 8.1 | 同包 | 同包 | 顺带能跑，不承诺 |
| Windows 7 非 SP1 | — | — | 无法启动，体检报告会明确告知 |
| Windows 11 | — | — | 不承诺（无 32 位版本）|

### 5.2 启动时自适应

应用启动时识别系统内核版本，自动选择图形策略，用户无需配置：

| 检测结果 | 图形策略 |
|---|---|
| Win7 / Win8 | 关闭窗口遮挡计算 + **软件渲染**（可用 `--force-gpu` 覆盖）|
| Win10 | **硬件加速**，不加任何降级开关 |
| Win11 | 硬件加速，日志记录「不在支持范围」警告 |
| 非 SP1 的 Win7 | 正常启动流程，但体检报告标红并说明原因 |

这套自适应的意义：**一个包打两个时代**。老机器求稳，新机器求快，不需要维护两套构建。

命令行开关（只用于排障与 CI，普通用户用不到）：

| 开关 | 作用 |
|---|---|
| `--software` | 无视系统等级强制软件渲染。CI 的无 GPU runner 靠它让自检可复现；现场白屏时也能用 |
| `--force-gpu` | 强制开启硬件加速，覆盖 Win7/8 的默认降级 |
| `--self-test` | 无头启动自检，跑完打印 JSON 并退出（CI 用）|
| `--self-test-out=<file>` | 把自检结果写到指定文件 |

### 6.1 四层职责

**① 主进程（唯一持有系统权限）**

| 模块 | 职责 |
|---|---|
| `platform-compat` ★ | 识别系统版本、支持等级，注入图形兼容开关 |
| `window` | 窗口创建、白屏兜底、崩溃恢复 |
| `logger` | 双写日志（内存环形缓冲 + 落盘），崩溃钩子 |
| `config` | userData/config.json 读写，缺字段自动补默认值 |
| `ipc/workspace` | 文件树、读写、新建、重命名、删除（进回收目录）|
| `ipc/ai` ★ | 中转站网关：地址归一化、SSE 流式解析、模型列表、中断 |
| `ipc/diagnostics` | 环境体检，生成可上报的诊断报告 |

**② 预加载层（唯一桥梁）**

- `contextIsolation: true` + `nodeIntegration: false`
- 只通过 `contextBridge` 暴露一个 `window.api`，**不暴露 `ipcRenderer` 本体**
- 渲染进程拿不到任何 Node 能力

**③ 渲染进程（React + Monaco）**

- 左侧文件树 / 中间多标签编辑器 / 右侧 AI 教学面板 / 底部输出面板
- 无 Node 权限，无外网直连

**④ 共享层**

- `shared/types.ts`：跨进程数据结构 + IPC 频道常量
- `shared/api.ts`：`AppApi` 接口，预加载必须实现，渲染按接口调用
- `shared/ai-endpoint.ts`：中转站地址归一化 + 错误码翻译
- `shared/language.ts`：扩展名 → Monaco 语言映射

## 7. Win7 兼容性专项

这是整个项目最容易翻车的地方，每条都对应一个真实的失败模式。

### 7.1 系统前提（缺一不可）

| 项 | 要求 | 缺失后果 |
|---|---|---|
| 系统版本 | **Windows 7 SP1（内核 6.1.7601）** | 非 SP1 无法启动 |
| KB2999226 | 通用 C 运行库（UCRT）| 缺 `ucrtbase.dll`，启动失败 |
| VC++ 2015-2022 运行库 | `msvcp140.dll` / `vcruntime140.dll` | 启动即报缺 DLL |
| 内存 | 建议 ≥ 2 GB | 内存不足时渲染进程被杀 |

这些全部写进了应用内的「**运行环境体检**」，学生装机后自己跑一遍就知道缺什么。

### 7.2 图形兼容（白屏 / 黑屏的头号原因）

Win7/8 上启动时自动注入：

| 开关 | 解决的问题 |
|---|---|
| `disable-features=CalculateNativeWinOcclusion` | Chromium 的窗口遮挡判定在 Win7 上不可靠，会把已显示窗口误判为被遮挡并暂停渲染 → **黑屏** |
| `disableHardwareAcceleration` + `disable-gpu`（默认）| 老显卡/虚拟机驱动在 GPU 合成路径上崩 → **白屏** |
| `use-angle=d3d9`（非软件渲染时）| 默认 ANGLE 走 D3D11，无 WDDM 1.1+ 的环境会失败 |
| `disable-direct-composition` | 规避窗口合成异常 |
| `backgroundThrottling: false` | 窗口失焦时渲染被节流，叠加遮挡问题容易假死 |

**Win7 默认软件渲染**。理由：教学机显卡状况不可控，软件渲染在 1080p 下编辑体验完全够用，而白屏是致命的。需要硬件加速时用 `--force-gpu`；反向地，`--software` 可在任何系统上强制软件渲染（CI runner 与现场排障用）。

### 7.3 启动兜底与故障自愈

| 场景 | 处理 |
|---|---|
| `ready-to-show` 8 秒未触发 | 强制 `show()`，避免窗口永不出现 |
| 渲染进程崩溃 | 弹原生对话框，一键「以软件渲染模式重启」|
| 页面加载失败 | `did-fail-load` 记录错误码 |
| 预加载脚本异常 | `preload-error` 记录堆栈 |
| 渲染进程 console | 全量转发进主日志，Win7 上不开 DevTools 也能定位 |

### 7.4 其他细节

| 项 | 处理 |
|---|---|
| 字体 | Win7 **没有** `Microsoft YaHei UI`，字体栈用 `Microsoft YaHei / Segoe UI / Consolas` |
| 用户数据目录 | 启动时用 `app.setPath('userData', %APPDATA%\AIEditor)` 显式固定（ASCII，避开非 ASCII 路径风险）。**不要依赖 Electron 的默认推断**：它取 `package.json` 的 `name`（`win7-ai-editor`），会和文档、CI 日志路径对不上 |
| 安装路径 | 体检检测非 ASCII 路径并告警 |
| 32 位系统 | ia32 包，CI 一并产出 |
| 更新机制 | **不做**自动更新，绕开签名与 SHA-2 依赖 |
| 安全边界 | Electron 22 已 EOL 无安全补丁，因此严格隔离外部内容：AI 响应只作文本渲染、预览用 `sandbox` iframe、不加载任何远程页面 |

## 8. AI 接入（中转站）

### 8.1 协议

OpenAI 兼容 `POST {base}/v1/chat/completions`，流式 SSE。中转站基本都实现了这套协议。

### 8.2 地址归一化

用户从中转站拿到的地址形式不统一，主进程统一收敛，避免「填错一个斜杠就用不了」：

| 用户输入 | 归一化结果 |
|---|---|
| `https://relay.example.com` | `https://relay.example.com/v1` |
| `https://relay.example.com/v1` | 不变 |
| `https://relay.example.com/v1/` | 去掉末尾斜杠 |
| `https://relay.example.com/v1/chat/completions` | 收敛回 `/v1` |

### 8.3 模型列表

中转站的模型名差异很大，手敲极易出错。设置页提供「**拉取模型列表**」，调 `GET {base}/v1/models` 填充下拉框，用户直接选。

### 8.4 兼容性设计

| 项 | 处理 |
|---|---|
| 自定义请求头 | 支持 `extraHeaders`，应对部分中转站的特殊鉴权要求 |
| 网络通道 | 用 Electron `net` 模块而非 Node http，**自动继承系统代理**（学校网络关键）|
| 超时 | 对话 120s，测试连接 / 模型列表 30s |
| 中断 | 支持 `aiAbort`，用户可停止生成 |
| 密钥安全 | 只存在主进程配置，渲染进程与 DevTools 都看不到 |
| 未配置时 | 编辑器功能完全不受影响，仅 AI 面板提示去设置 |

### 8.5 错误码翻译

中转站最常见的几类失败，直接翻译成用户能照做的中文提示：

| 状态码 | 提示 |
|---|---|
| 401 | 鉴权失败：密钥无效或已过期 |
| 402 | 余额不足：中转站账户额度已用完 |
| 403 | 无权访问：密钥可能不允许调用该模型 |
| 404 | 地址或模型不存在：确认是否 OpenAI 兼容的 `/v1` 端点 |
| 429 | 触发限流：请求过于频繁 |
| 5xx | 中转站服务异常，请稍后重试 |

### 8.6 教学助手的三档模式（M1）

不是简单套一个聊天框，而是按教学环节预置 prompt 模板：

| 模式 | 触发 | 行为 |
|---|---|---|
| 讲解模式 | 选中代码 → 点「讲解」| 先一句话说这段代码在做什么，再逐行解释，最后给一个小改动练习 |
| 纠错模式 | 粘贴报错 → 点「诊断」| 定位到具体行，解释原因，给修改后的完整片段 |
| 出题模式 | 指定知识点 → 点「出题」| 生成练习题 + 隐藏参考答案 + 判定要点 |

## 9. 打包与 CI

### 9.1 产物（仅 2 个）

```
AIEditor-<version>-win7-win10-x64.zip    64 位系统
AIEditor-<version>-win7-win10-ia32.zip   32 位系统
```

zip 内除程序外还包含 `使用说明.txt`，写明该用哪个包、启动失败怎么排查。

### 9.2 只在 CI 打包

项目约定：**开发环境不做 Windows 打包**。`npm run dist:win` 会先执行 `scripts/guard-ci.mjs`，检测不到 CI 环境就直接拒绝执行（确需本地打包需显式设 `ALLOW_LOCAL_DIST=1`）。

理由：交叉打包要拉取目标平台的 Electron 二进制与工具链，既慢又容易和 CI 产物不一致，测出来的结论没有意义。

### 9.3 CI 流程

```
push main / push tag / 手动触发
  → windows-2022 runner + Node 20
  → npm ci
  → npm run typecheck
  → npm run build            （含 chrome108 / node16 目标护栏）
  → npm run dist:win         （x64 + ia32，两个 zip）
  → 启动自检 A（门禁）：--self-test --software，失败即中断构建
  → 启动自检 B（仅记录）：--self-test 默认图形路径，失败不阻断
  → 产物清单：名字 / 大小 / SHA256 写进日志 + 上传 Artifacts
  → 发布 Release：main 推送 → 滚动 latest（prerelease）；推 v* tag → 正式 Release
```

产物有两处可拿，日常用 Release：

| 位置 | 路径 | 说明 |
|---|---|---|
| **Releases 页** | `releases/tag/latest`（main 滚动）/ `releases/tag/v0.1.0`（正式）| 好找，链接可长期分享，**推荐** |
| Artifacts | 工作流**运行页**（不是任务日志页）底部 | 额外带自检报告，默认 90 天后过期 |

> 把「产物清单」写进日志是有意为之：Artifacts 面板只在运行页底部，很容易找不到；
> 日志里有名字、大小和 SHA256，就能直接判断产物到底有没有生成、是不是完整。

**启动自检是这里最有价值的一步**：它把「能打包但一启动就白屏」的产物挡在发布之前。
应用支持 `--self-test`：启动 → 等渲染进程加载 → 在页面内执行自检脚本 → 输出 JSON 并退出。
检查项包括主进程启动、页面加载、React 挂载、Monaco 实例化、IPC 通道可用。

两个必须注意的实现细节：

1. **runner 上没有真实 GPU**，所以门禁那一次显式加 `--software`。否则图形路径取决于 runner 的虚拟显示设备，自检结果会随机，甚至把正常的包误判为失败。
2. **自检必须等，不能瞬时采样**。`__SELFTEST__` 是在 `did-finish-load` 那一刻被主进程调用的，
   而 React 18 并发渲染尚未提交、`store.init()`（含 IPC 往返）也还没回来。
   所以每一项检查都要轮询等待（`waitFor`），否则自检必然随机失败。
   主进程侧再加一层 90s 软超时 + 120s 硬看门狗，保证卡死时能给出结论，而不是挂到 job 超时。

> 注意：CI 跑在 Windows Server 2022 上，能验证「Windows 上能否启动」，
> 但**不能替代 Win7 真机验证**。真机测试清单见 `docs/多系统-测试清单.md`。

### 9.4 构建期的版本敏感点

依赖版本钉死的同时，**配置字段也有版本边界**。这类错误只在真正打包时才暴露，
而本项目只能在 CI 打包，一轮就是十几分钟，所以改配置时先在本地自查：

| 项 | 事实 | 后果 |
|---|---|---|
| `win.signtoolOptions` | electron-builder **24.x 没有这个字段**（25+ 才引入），且 `win` 对象是 `additionalProperties: false` | 写了会因 schema 校验失败**直接中断打包** |
| 「不签名」怎么做 | 不配任何证书 + CI 里 `CSC_IDENTITY_AUTO_DISCOVERY=false` 就够 | 不需要任何额外字段 |
| `preload` 的构建目标 | electron-vite 强制要求 `node*`，写 `chrome108` 会报 `must be "node?"` | 预加载脚本跑在 Node 上下文，目标本就该是 `node16` |

不打包也能校验配置（本地跑，几秒出结果）：

```bash
node -e "const y=require('js-yaml'),f=require('fs');require('app-builder-lib/out/util/config.js').validateConfig(y.load(f.readFileSync('electron-builder.yml','utf8')),{isEnabled:false,add:()=>{}}).then(()=>console.log('配置 OK')).catch(e=>{console.error(e.message);process.exit(1)})"
```

## 11. 风险清单

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | 机房机器不是 Win7 SP1 | 完全无法启动 | 使用说明 + 体检报告明确告知 |
| 2 | 缺 VC++ 运行库 | 启动报缺 DLL | 体检检测并引导安装 |
| 3 | 老显卡 GPU 崩溃 | 白屏 | 默认软件渲染 + 崩溃自愈重启 |
| 4 | 32 位机型 | x64 包跑不了 | 同版本提供 ia32 包 |
| 5 | Electron 22 已 EOL | 无安全补丁 | 严格隔离外部内容；评估周期内可接受 |
| 6 | Monaco 升级引入新特性 | Win7 白屏 | 版本钉死，升级必须真机回归 |
| 7 | 新语法 / 新 CSS 漏入 | 白屏或样式错乱 | 构建 target 护栏 + 真机回归清单 |
| 8 | 学校网络无法访问中转站 | AI 不可用 | 支持自定义端点与代理；编辑器功能不受影响 |
| 9 | 中转站密钥被滥用 | 费用损失 | 密钥只在主进程；建议用限额密钥 |

## 附录：一句话总结

> 在 Win7 这个前提下，**Electron 22.3.27 + Chromium 108 构建目标** 是唯一可行的技术底座；
> 方案的重点不在选了什么框架，而在三件事：
> **把版本上限变成编译期护栏**、**让同一个包自适应两个时代的系统**、
> **在只有 CI 能打包的约束下，用启动自检把白屏产物挡在发布之前**。
