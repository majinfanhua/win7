## 一、系统设定（`系统.md`）

### 是什么

发给模型的 system prompt 不再是设置里的一段自由文本，而是**一个真实存在的
Markdown 文件**：`<userData>/系统.md`。用户可以打开看、能确认「AI 到底收到了什么」。

组装规则在 `src/shared/system-doc.ts`（纯函数，可单测），落盘与一致性维护在
`src/main/system-doc.ts`。

### 文件长什么样

按「从最稳定到最易变」排列：

| 顺序 | 段落 | 内容来源 | 变化频率 |
|---|---|---|---|
| 1 | 你的身份 | 设置里的 AI 命名、对用户的称呼 | 几乎不变 |
| 2 | 你要做什么 | 设置里的默认提示词 | 几乎不变 |
| 3 | 用户的习惯 | 设置里的习惯 | 偶尔 |
| 4 | 本机环境 | 自动探测的运行时 + 操作系统 | 换机器/装新工具才变 |

**这个顺序不是为了好看，是为了钱。** 主流中转站（OpenAI / DeepSeek）的 prompt
缓存按「最长公共前缀」计价：前缀里有一个字节不同，它后面的全部内容都不算命中。
把易变内容放最后，用户装了个 python 只会让最后一段失效；反过来放，一次环境
变化会废掉整段缓存。

文件里**刻意没有时间戳** —— 时间戳每次都不同，写进去等于每次请求都让缓存失效，
而且变的正是最前面那几行。想看生成时间就看文件的修改时间（mtime），那个不进 prompt。

### 只在三个时机写盘

1. 设置页保存后点「查看全文 / 重新生成」
2. 一次对话即将开始时（`ensureSystemDoc`）
3. 文件被删或状态异常时自愈

**不在每次请求前重写**：写文件本身便宜，但它会改 mtime，用户就分不清
「这是我改的还是它自己变的」。会话内的请求走内存快照。

### 手改检测用 hash 而不是 mtime

mtime 会被任何一次触摸改变（编辑器保存、同步盘回写、备份软件扫描），
拿它判断「用户改过」会频繁误判，然后就是「我什么都没改，它却把我的话盖了」。
hash 只认内容：内容一样就一个字都不动。

旁文件 `<userData>/系统.md.sha256` 记「上次我们写出去的是什么」，
用来判断当前文件是「我们自己写的旧版本」还是「用户改过的」。

**用户手改后，下次会话前会被覆盖回设置内容**（这是明确的产品要求）。
所以文件开头的注释里写清了「要改请去设置里改」，让这个文件不只是拒绝，而是指路。

### 会话级快照：为什么需要 sessionId

`aiChat` 会带上当前会话 id。主进程用它判断「这是不是一次新会话」：

- **同一会话内**：复用快照。会话中途用户手改了文件也不会影响正在进行的对话
  （否则前后两轮的 system prompt 不一致，模型行为会莫名变化，而且每轮都会挂掉缓存）
- **新会话**：重新校验并覆盖手改，设置改动立刻生效
- **不传 id**（后台总结）：沿用当前快照 —— 它必须用与对话时**完全相同**的
  system prompt，否则缓存前缀对不上，省钱的意图就落空了

这三种行为都有测试钉住（`scripts/check-profile-io.mjs`）。

### 名字长度为什么限 5 个字

名字会出现在每一句自称里，太长会挤占上下文。界面用 `maxLength` 限一次，
`normalizeAi` 在写入时再夹一次 —— **界面不是安全边界**，手改 config.json
或从 devtools 调 `setConfig` 都能绕过去。

### 文件读写为什么整体加锁

「写内容」和「写 hash」如果交错执行，会留下「内容是 A 的、hash 是 B 的」状态。
后果不是数据损坏，而是每次会话都判定「不一致」并重写一遍 ——
表现为「这个文件老是自己在变」。所以两步放在一个锁里（`atomic-file.ts`）。

## 二、归档与总结

### 三种命运

一条会话可以继续用、删掉、或**归档**。归档 = 明确宣布「这段结束了，可以总结了」。

只有归档过的会话才会：

- 被 AI 生成一段梗概
- 进入 AI 可检索的范围（`listSessions` 能翻到）

**没归档的一概不处理。** 两条理由：用户可能只是切出去倒杯水，总结就是白花钱；
总结一份还在增长的记录必然要重做，而重做意味着重复付费。
这个「显式宣布结束」的动作把判断权交给用户，比任何自动启发式都准。

### 归档后为什么立刻总结

这里有一个真实的省钱机制：

prompt 缓存按最长公共前缀算。归档发生在一段对话刚结束之后，而总结请求的消息是
`[system prompt, ...这段对话的全部消息, 一句「请总结」]`——
**前面那一整段与刚才最后一次请求完全相同**。所以：

- 服务商侧还热着的缓存被直接命中，那几千 token 按十分之一计价
- 攒到明天再批量总结，缓存早过期了，同样的内容要按全价再买一次

两个前提必须同时满足，代码里对应两处：

1. **system prompt 要与对话时一致** → `sessionSystemPrompt()` 返回的是同一个快照
   （这就是它「不传 sessionId 时沿用快照」那条分支的用途）
2. **tools 字段要一起发** → 服务商把 tools 排在消息之前，少发 tools 会让整个
   前缀错位、缓存全丢。代价是模型可能真去调工具，所以处理了「返回空正文」
   的情况：那就是它想调工具，这时去掉 tools 再试一次（第二次必然不命中缓存，
   但正确性优先于省钱）

### 长会话的例外

超过 120 条消息的对话全带上会超出上下文窗口（总结请求失败，用户什么也得不到）。
这时退回「取头取尾」：开头（问题是什么）+ 结尾（结论是什么）。
这种情况缓存基本不可能命中，但至少不会失败。

### 索引为什么单独一份（`archive.json`）

`recentSessions` 上限 **20 条**，而归档是「长期资料」—— 第 21 条归档进来时
最早的会被挤掉，它的梗概也跟着消失，而梗概正是归档唯一的价值所在。

所以归档索引单独存一份，不设条数上限（每条只有标题 + 梗概）。

### 归档状态为什么存在于三处

| 位置 | 用途 |
|---|---|
| `sessions/<id>.json` 的 `archivedAt` / `summary` | 换机器拷走 sessions/ 时状态跟着走；最终依据 |
| `config.json` 的 `recentSessions[].archived` | 左侧列表每次启动整份读，不能为它逐个读正文 |
| `sessions/archive.json` | AI 检索用，不设条数上限 |

**这不是冗余，是三层各有各的用处。** 三处同步的两条纪律：

- `sessionSave`（界面每次落盘）**从磁盘上的旧文件继承**归档字段，
  不接受渲染层传进来的值 —— 否则用户归档之后随便说一句话，
  落盘就会把归档标记抹掉，现象是「归档的会话自己变回未归档」
- `upsertSession`（touch 时更新索引）也继承 `archived`，理由同上

### 总结失败的上限

`attempts` 到 3 次就停止自动重试。没有这个上限的话，一条必然失败的会话
（比如归档后用户把 API Key 删了）会在每次启动时重试一次，
用户只会看到「启动时莫名卡一下」。

### 启动补做为什么延迟 8 秒、只做 2 条

启动瞬间要建窗口、加载渲染进程、探测运行时，这时插一个网络请求会跟它们抢资源，
用户能感觉到「开机慢」。8 秒后界面已经画出来了。

补做是串行的，每条要几秒。攒了十条的话启动后头一分钟都在发请求。
每次最多两条，剩下的下次启动继续，几天内自然清空。

### 并发：一个真实踩到的 bug

**现象**：日志里 `rename ... archive.json.tmp -> archive.json` 报 ENOENT，
并且有一次归档**静默丢失**。

**原因**：归档会「先写索引，再在后台总结」，而总结流程里还要再写一次索引。
两条路径并发写同一个 `.tmp`：

```
A: 写 tmp
B: 写 tmp（覆盖掉 A 的内容 —— A 的数据已经丢了）
A: rename tmp → target（成功，但写进去的是 B 的内容）
B: rename tmp → target（ENOENT，tmp 已经被 A 挪走了）
```

**修法**（`src/main/atomic-file.ts`）：

1. `atomicWriteFile` —— 同一路径的写排队执行（每个路径一条 Promise 链），
   tmp 名字带 pid + 序号，不同路径互不阻塞
2. `withLock` —— 「读—改—写」整体串行。**光有原子写不够**：两个并发归档
   各自读完索引、各自改、各自写，后写的会覆盖前一次加的条目。
   原子写保证的是「文件不半截」，不是「改动不丢」，两件事都要做

`scripts/check-profile-io.mjs` 里有「并发归档 5 条一条都不丢」与
「并发『取消 + 新增』两个动作都生效」两个测试钉住它。

### 并发时的重跑而不是丢弃

`summarizePending` 正在跑时，新的请求**不能简单丢掉** —— 用户刚点完归档
如果正好撞上启动补做，丢掉就意味着「要等下次启动才会总结」，
而那一刻正是缓存最热、最该立刻总结的时候。

所以用「还有活要干」的标记：正在跑时后来的请求只打标记，
当前这轮结束后立刻再跑一轮。既不并发，也不漏掉。

### 一条被拆掉的循环 import

原来的结构里有一条真实的环：

```
archive.ts → tools/index.ts（要工具表来发总结请求）
           → tools/session-tools.ts（AI 用的 listSessions/readSession）
           → archive.ts（要归档索引）
```

它当时是**良性**的 —— 所有跨模块调用都在函数体里（不是模块顶层），
所以运行时拿到的是加载完的模块。但它是定时炸弹：哪天有人在顶层写一句
`const X = listArchive()`，就会拿到半成品模块，报 `is not a function`，
而且**只在特定加载顺序下复现**（开发时可能一直不复现，打包后才炸）。

拆法：会话工具只需要「读索引」，不需要「归档 + 总结」那套业务。
把存储层抽成叶子模块 `archive-index.ts`（只依赖 atomic-file / logger / shared），
环就断了。这个约定在本项目里已有先例：`tools/meta.ts` 也是为了让能力探测
不断环才不依赖任何工具实现的。

`scripts/check-profile-io.mjs` 里有一个**通用的依赖环检测**（深度优先扫
`src/main` 下所有相对 import）。它验证过是有效的 —— 故意造一个环时，
失败信息会直接给出环的路径。

## 三、持久记忆

### 两个文件的分工

| 文件 | 用途 | 谁写 |
|---|---|---|
| `memory/MEMORY.md` | 长期记忆，精选过的、跨会话仍然成立的 | AI 主动写 |
| `memory/YYYY-MM-DD.md` | 当天流水，随手记 | AI 主动写 |

分开的理由：如果只有一个文件，AI 每次「记住一件事」都要重写整份记忆，
而重写有风险（模型改写时可能丢掉旧内容）。流水文件只追加，
不存在丢掉旧内容的可能；精选文件才需要改写，而它改动的频率低得多。

### 为什么是 Markdown 而不是数据库

记忆最怕「用户不知道它记了什么」。存进 SQLite 或向量库之后，用户对它的唯一接口
就是这个应用的界面 —— 而界面总会漏掉一些东西。存成 Markdown 的好处：

- 用户可以用记事本打开、直接改、直接删
- 出问题时能一眼看出「它记错了什么」，而不是面对一个黑盒
- 换机器时拷一个文件夹就是完整迁移

这个思路来自 OpenClaw：**工作区里的纯文本文件是唯一真相**，
索引 / 向量只是加速手段，丢了也能从文本重建。

### 写入用 appendFile 而不是整份覆盖

后者在两次操作之间丢一行就永久丢了，而记忆是只增不减的东西，丢一行的代价很高。
超过 256 KB 就拒绝并**报错**（而不是静默失败）—— 静默失败会让模型以为记住了。

### 读取时必须脱敏

用户完全可以自己打开 `MEMORY.md` 手写一段密钥进去 —— 写入时的扫描拦不住手写。
而读出来的内容会进对话上下文、被发到中转站。
**所以读这条路上再扫一次**，把命中的凭证换成 `[已隐去：类别]`。
这是唯一能兜住手写内容的关口。

用替换而不是截断：截断会破坏对话结构，而模型看到 `[已隐去：OpenAI API Key]`
仍然能理解「这里原本有个密钥」。

## 四、用量统计

### 只按天聚合，不存每一条请求

「每一条都记」能画很细的图，但文件会无限增长，而用户真正想知道的问题只有三个：

- 今天用了多少（会不会把额度聊爆）
- 这一周的趋势（是不是越来越费）
- 缓存命中率高不高（省钱手段有没有生效）

按天聚合就够答了。文件大小与使用时长无关（恒定几十行）。

### 估算值与实际值分开记

中转站不回 usage 时，代码会按字数估算。这类数字误差可能有几倍，
混进总数会让「今天 12.3 万 token」这个看起来精确的数字其实一半是猜的。
所以每个桶都带 `estimatedRequests`，界面会标注「其中 N 次为估算」。

### 日期用本地时区

用 UTC 的话，东八区晚上 8 点之后会被算成第二天 —— 用户晚上聊了一大段，
统计页显示「今天 0」。这是很典型的「看起来像 bug 但其实是时区」问题。

### 写盘：防抖 2 秒 + 原子替换 + 退出前 flush

一次对话会产生好几次 HTTP 往返，每次都落盘的话一个长对话要写几十次小文件。
代价是「刚聊完就断电」会丢最后两秒 —— 这个功能不是账本，丢一点无所谓。

但**「聊完立刻关窗口」是常见操作**，所以 `before-quit` 里显式 flush 一次。
用同步写：那个时机里 Promise 不保证能跑完。

### 脏数据不能让统计页崩掉

`usage.json` 是用户可见可改的文件。读取时逐字段收敛（负数和 NaN 归 0、
只认形状对的日期 key），坏文件的最坏后果是「统计清零」，不是「应用起不来」。

## 五、敏感信息扫描

`src/shared/secret-scan.ts`，纯函数，9 条规则。

### 认哪些形状

PEM 私钥头、`sk-ant-` / `sk-`（含 `sk-proj-` 这类带连字符的新格式）、
`ghp_` 等 GitHub token、`AKIA`、`xoxb-`、`AIza`、三段式 JWT。

### 为什么不拦「看起来像密码」的东西

**误报的代价是真实的**：AI 想记一句「用户的环境变量叫 DB_PASSWORD」都被拒，
那这个功能就没法用了 —— 用户会直接把它关掉，那才是真的失去保护。
所以只认那些**有固定形状、几乎不可能是巧合**的凭证格式。

也不做「按熵值猜」：高熵字符串在正常代码里到处都是（hash、base64 图标、
压缩数据），按熵拦会拦到一堆正常内容。

### 测试里两组同等重要

`scripts/check-profile.mjs` 里「必须认出的形状」和「绝不能误报的内容」
是同等重要的两组。另外每条规则都要**单独**验证能匹配自己的样本，
以及**只**被一条规则命中 —— 否则界面上会报「检测到 OpenAI API Key、
Anthropic API Key」这种把同一个密钥算成两类的提示。

### 拒绝理由里不能带原文

带了的话密钥就跟着错误信息进了对话上下文与日志，
本来要防的事情反而被自己做了。有测试钉住这一条。

### 测试样本为什么在运行时拼出来

第一次提交这份代码时被 GitHub 拦下来了：

```
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote:   - GITHUB PUSH PROTECTION
remote:     - Push cannot contain secrets
remote:       —— Slack API Token ——
remote:        path: scripts/check-profile.mjs:202
```

**讽刺的是：是我自己写的敏感信息扫描器的测试样本，触发了 GitHub 的扫描器。**

这是两边都对的冲突：仓库要拦真密钥，而测试需要**形状逼真**的样本 ——
样本不像真凭证，规则就匹配不上，测试也就失去了意义。

解法是**在运行时拼出来**（`scripts/lib/fake-secrets.mjs`）：

```js
export const FAKE_SLACK = 'xo' + 'xb-' + '123456789012' + '-abcdefghijklmn'
```

源码里不存在任何「看起来像密钥」的连续字符串，推送保护扫不到；
而运行时的值完全符合各家格式，规则照样命中。

**为什么不用「明显的占位符」**：把样本写成 `sk-XXXX` 确实不会被拦，
但测试就废了 —— 规则要求「`sk-` 后至少 20 个字符」，`XXXX` 只有 4 个，
于是这条测试再也证明不了规则是对的。样本必须满足长度要求，没有捷径。

### 怎么自查有没有漏网的

提交前跑一遍（与扫描器同源的形状）：

```bash
grep -rnE "sk-[A-Za-z0-9_-]{20,}|gh[pousr]_[A-Za-z0-9]{20,}|xox[baprs]-[A-Za-z0-9-]{10,}|AKIA[0-9A-Z]{16}|AIza[0-9A-Za-z_-]{35}" \
  --include="*.ts" --include="*.tsx" --include="*.mjs" --include="*.md" . | grep -v node_modules
```

## 六、AI 能用的新工具

| 工具 | 做什么 | 门控 |
|---|---|---|
| `listSessions` | 列归档会话（只有标题 + 梗概） | 无（不需要外部程序） |
| `readSession` | 读一条归档会话的正文，按行分页 | 无 |
| `memoryGet` | 读长期记忆 + 当天流水 | 无 |
| `memoryWrite` | 记一笔（默认当天流水） | 无 |

### 为什么做成工具而不是塞进 prompt

见下一节。

### 为什么要分开 `MEMORY_TOOLS` 一组

它们操作的不是工作区，而是**应用自己的数据**，所以不能走 `assertInsideRoot`
（那条检查会把它们全挡掉）。单独一组是为了让「AI 能碰什么」在设置界面里
仍然分得清层次：文件是学生的代码，这一组是 AI 自己的笔记本。

### 保守模式为什么不关掉它们

「保守模式」限制的是「能对我的代码做什么」。记忆与会话检索碰不到工作区，
把它们也关掉只会让「保守模式」变成「阉割模式」，与它的本意无关。

### `readSession` 的两条约束

1. **分行返回**并告诉 AI 读到的是哪一段。一个会话可能几万字，
   全塞进上下文有撑爆窗口的风险，也会让有用内容被稀释
2. **返回前脱敏**。会话正文里可能躺着用户粘过的密钥

---

## 七、为什么不把记忆塞进 system prompt

这是整个设计里最要紧的一条，也是与「设置改了缓存失效无所谓」的区别所在。

prompt 缓存按最长公共前缀算。如果把「有哪些历史会话」「记忆里写了什么」
拼进 system prompt：

- 用户刚归档一条会话 → 列表变了 → 从 system prompt 那一行往后**全部**重算
- AI 刚写了一条记忆 → 下次请求又全变

一次长对话要发十几次请求，每次都在最前面变，缓存等于完全没有。

做成工具之后，这些内容出现在对话的**末尾**（工具调用与返回值），
前面稳定的 system prompt + 历史消息照样命中缓存。代价是 AI 要多花一轮去查 ——
但它只在真的需要时才查，而塞进 prompt 是每一轮都付钱。

**设置项可以随便改、改了缓存失效无所谓**（用户明确说过），
因为设置一天改不了几次；**记忆一次对话里可能改好几次**，所以必须走工具。
