# 参考 LiveAgent 的改造：做了什么、没做什么

本文记录**参考 [LiveAgent](https://github.com/Stack-Cairn/LiveAgent) 对本站项目所做改造**的完整账目，包括：

- 哪些功能移植了、为什么值得移植
- 哪些功能**没有**移植、具体卡在哪（这篇文档的主要价值在这部分）

参考项目的本地副本在 `参考项目-LiveAgent/`（已在 `.gitignore` 里锚定忽略，绝不入库）。
它是 Tauri 2（Rust + React）项目，与本项目的 Electron 22（TypeScript）栈不同，
所以能拿的是**算法与设计**，不是代码本身。

---

## 一、总体结论

LiveAgent 是一个成熟的本地优先 AI 代理桌面端，规模约 **122,000 行 Rust + 约 14,000 行 TS 工具层**。
本项目约 15,000 行。

关键发现：**它的 AI 工具层、压缩策略层是 TypeScript**（`src/lib/tools/`、`src/lib/chat/compaction/`），
不依赖 Rust 与 Tauri。这部分是本次移植的主要来源 —— 算法可以直接翻译过来，
不需要引入任何原生模块，也就不受「Win7 不能用原生模块」这条硬约束的限制。

判断能不能移植的标准始终是同一条：
**这个功能会不会引入原生模块、需不需要 Win10+ 的系统 API、要不要 git 之类的额外依赖。**

## 二、已移植（5 项）

### 1. Edit 宽容匹配级联 —— `src/main/tools/edit-match.ts`

**移植自** `commands/workspace/edit_match.rs`（834 行）。

**原来是什么样**：`editFile` 用 `indexOf` 精确匹配。模型复述文件内容时只要有一个字符
对不上（CRLF 文件给了 LF、行尾多/少一个空格、整段缩进差一级），就直接失败。
这在实践中非常常见 —— 模型"记得"的内容与磁盘上的字节总有细微出入。

**现在是什么样**：四级级联，**从严到宽**依次尝试，第一个匹配上的级别获胜：

| 级别 | 放宽了什么 |
|---|---|
| `exact` | 不动（原行为，优先） |
| `line-endings` | 归一化 CRLF/LF，忽略开头的 BOM；替换文本按文件原有换行风格重渲染 |
| `trailing-whitespace` | 按整行窗口比较，忽略每行行尾空白 |
| `indentation` | 整行窗口，所有非空行统一平移同一段前导空白 |

两个刻意的设计选择：

1. **缩进那一级只接受「统一偏移」**。相对缩进不一致时（文件是 8/16，模型给 4/8）
   一律拒绝，而不是硬套一个前缀 —— 那会把代码结构改错。测试里
   `缩进：相对缩进不一致时拒绝` 钉的正是这个。
2. **把用了哪一级回报给模型**。否则模型不知道自己给的空格是错的，下一轮还会照错的方式给。

**验证**：`npm run check:editmatch`，16 项。包括末尾无换行、BOM 保留、
中文与 emoji 不被切坏（UTF-16 码元边界）、多字节替换等。

### 2. 读陈旧检测（stale-read）—— `src/main/tools/file-tools.ts`

**移植自** `commands/workspace/fs.rs` 的版本校验部分。

**解决什么问题**：原来只记「本进程读没读过这个文件」（`whole: boolean`）。
这挡得住「AI 没读就想整篇覆盖」，挡不住「读完之后文件被别的程序改了」——
学生用记事本改了代码，AI 再照旧的记忆去改，就把人的修改冲掉了。

**现在**：读文件时记下 `mtimeMs + size + 内容哈希`；写之前比对，
变了就拒绝并让模型重读。两个细节：

- **只对「完整读过」的文件生效**。片段读记下的哈希是那一小段的内容，
  拿它跟整个文件比必然不等，会误报 —— 这个坑在实现时踩到过，注释里写明了。
- **mtime 变了不代表内容真变了**（有些编辑器与同步盘会空写一遍），
  所以再比一次哈希，避免无谓地打断模型。

### 3. 工具参数截断守卫 —— `src/main/tools/argument-guard.ts`

**移植自** `lib/chat/runner/toolCallArgumentGuard.ts`（128 行）。

**解决什么问题**：流式返回的工具参数是分片拼的。连接在参数传到一半时断掉，
拼出来的是残缺 JSON。危险的不是它拼不出来，而是**有些残缺片段恰好能被
"宽容修复"成看起来合理、实际错误的值**：

```
{"path":"C:\Users\
```

补成 `{"path":"C:\Users\"}` 就成了另一个真实存在的目录，执行下去就改了不该改的东西。

**判定逻辑**要能区分四种流形态，而它们的最终字符串几乎一样：

| 形态 | 判定 |
|---|---|
| 正常增量流 | 拼起来是完整 JSON → 健康 |
| 累计快照流 | 拼起来坏，但最后一片单独看完整 → 健康 |
| 重复帧流 | 同上 → 健康 |
| **真截断** | 拼起来坏，且**没有任何单独一片完整** → 拒绝执行 |

**这里比参考实现多堵了一个洞**：参考实现只在「残缺 buffer 的宽容补全**恰好等于**
最终参数」时报错。但停在字符串中间的截断**补不出合法 JSON**，
于是被判成「无害」放行了 —— 而这恰恰是最危险的一类（路径被切断）。
现在统一为：凡是没能形成完整 JSON、又没有独立完整副本的，一律报截断。
测试 `真截断（停在字符串中）：必须报截断` 覆盖了这个分支。

被拒绝的调用会把原因作为工具结果回灌，让模型重新发起，而不是静默失败。

**验证**：`npm run check:argguard`，13 项。

### 4. 命令安全三件套 —— `src/main/command-safety.ts`

**移植自** `runtime/sandbox.rs` 里**与沙箱无关的纯逻辑**部分（这部分是本次意外收获）。

报告明确指出沙箱整体不能移植（见下节），但其中三个工具函数是纯字符串/路径逻辑，
与 Win32 安全 API 无关，Win7 完全可用：

**a. `quoteArg()` —— 按 `CommandLineToArgvW` 真实规则加引号**

关键在**末尾反斜杠**：`"C:\Program Files\"` 里最后那个 `\` 会把收尾引号转义掉，
引号配不上，后面的参数全部错位。必须在收尾引号前把反斜杠翻倍。

> 本项目原本通过「把命令写成临时 `.cmd` 文件」绕开了这个问题（见 `shell.ts` 注释），
> 所以这个函数目前不是关键路径。但它是正确实现，留着备用并加以测试。

**b. `resolveProgramInPath()` —— 绝不回落到工作区（防二进制投毒）**

**这是本次最实用的一项加固。** Windows 的 `CreateProcess` 在程序名是「部分名」时，
会拿**当前目录**补全而**不查 PATH**。而子进程的 cwd 恰好是工作区 ——
**那是模型能写文件的地方**。

后果：模型只要在工作区里写一个 `taskkill.bat`，我们「杀进程」的动作就变成执行它的脚本。
所以现在：只搜索 PATH 里的**绝对目录**，剔除 `.`、空串、相对项；
解析不到就**宁可不执行**，也不退回裸名。

本项目的两处实际修复：
- `shell.ts` 的 `cmdPath()` 原本兜底 `return 'cmd.exe'`（裸名）→ 改为解析绝对路径，失败返回 `null`
- `exec.ts` 的 `spawn('taskkill', ...)` → 改为绝对路径，解析不到就跳过这层

**c. `checkWorkspaceSafety()` —— 拒绝把凭据目录交给 AI**

工作区根取成 home 或磁盘根时，AI 的读写围栏等于没有。
现在会在打开工作区时检查并**记一条警告日志**（不阻止打开）。

> 刻意**只警告不阻止**：这是教学工具，直接拒绝会变成
> 「老师打不开自己的课件文件夹」这种莫名其妙的故障。风险本身可解释就够了。

**验证**：`npm run check:command-safety`，30 项。

### 5. 上下文预算与压缩策略 —— `src/main/compaction-policy.ts`

**移植自** `lib/chat/compaction/policy.ts`（181 行）与其常量。

**解决什么问题**：一次提问里，历史消息是**全部**发给模型的。教学场景下学生
常在一个会话里连问十几轮，还夹着 readFile 读进来的整段源码，
很快撞上窗口上限，中转站返回 400，表现为「聊到一半突然不能用了」。

**移植了策略层，没移植存储层**（那需要 ~5,500 行与 Segment/Checkpoint 数据结构）。

阈值公式照搬：`contextWindow − maxOutputToken × 因子`，因子 1.2 / 1.5。
必须给模型的回答留空间，否则输入刚好占满、输出没地方放，照样报错。

**内置了一张模型窗口表**（GPT / Claude / Gemini / DeepSeek / Qwen / GLM / Kimi 等）。
中转站的 `/models` 只给模型名、不给窗口大小，没有这张表就只能全按最小值算。
匹配不到时退到保守值 —— 代价不对称：估大了直接撞墙报错，估小了只是提前压缩。

同时留了**手动填写窗口**的口子，给「内置表过时了」留自救路径。

**实际接入**（`src/main/ipc/ai.ts`）：
- 每轮发请求前**裁剪旧的工具输出**（第一道防线，零成本、无副作用）
  只裁工具输出、且保留最近 4 条 —— 这些内容模型可以再读一次，
  而用户的提问和模型的回答不能重来，裁掉等于篡改对话
- 仍然超预算就**明确拒绝并说清原因**，而不是让用户对着
  `context length exceeded` 发懵

> 刻意**不做自动总结压缩**：那要额外发一次请求、要花钱、要等，
> 而且总结错了会静默丢信息。教学场景里「明确告诉用户该开新对话了」
> 比「悄悄丢掉一半历史」更可解释。

**验证**：`npm run check:budget`，44 项。含一个「配置留 0 = 自动」与
「判定里 0 = 窗口未知」语义相反、接错就静默失效的陷阱测试。

### 附带修复（不在原计划内）

**`atomicWrite` 在 Windows 上可能丢两份内容**（`file-tools.ts`）

参考项目的 checkpoint 实现里有一段 Windows 专用的 rename 备份舞蹈。
对照之下发现本项目的 `atomicWrite` 直接 `rename(tmp, target)` 覆盖已存在的文件——
目标被占用（杀毒软件、编辑器、同步盘都会短暂占住）时，这一步可能
**既失败、又已经把原文件弄没了**。

现在改为：先 `rename(target → backup)` 把原件挪开，再 `rename(tmp → target)`；
第二步失败就把 backup 挪回去。任何时刻磁盘上都至少有一份完整内容。

## 三、没有移植，以及为什么

### ❌ 沙箱 —— 明确不可行

LiveAgent 有一套 3,211 行的 Windows 沙箱（AppContainer / Low IL token）。
**在 Win7 上完全跑不起来，且不是"降级运行"而是"直接失败"**：

| 机制 | 需要 | Win7 |
|---|---|---|
| `CreateAppContainerProfile` | Win8+ | ✗ |
| `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` (0x20009) | Win8+ | ✗ |
| `DeriveCapabilitySidsFromName` | Win8+ | ✗ |

更要命的是：`win::execute()` **在两条路径上都无条件调用**
`derive_appcontainer_profile_sid()?`，所以 AppContainer 与
「duplicated Low-IL token」两条后端在 Win7 上都在同一个 `?` 处硬失败。

唯一在 Win7 可用的机制（`CreateRestrictedToken(WRITE_RESTRICTED)`）
**已被作者试过并主动否决** —— 它会让 Schannel 返回 `SEC_E_NO_CREDENTIALS`，**HTTPS 全挂**，
现仅存于 `#[cfg(test)]`。

**本项目的处置**：不移植，也不假装有。本项目的能力分层本来就有
「设置上限 ∩ 本机探测」两层（见 `capabilities.ts`），命令执行的
安全边界是**工作区围栏 + 上面第 4 项的三道加固**，不宣称沙箱隔离。

### ❌ 子代理 + Git worktree 隔离

隔离机制是真实的 `git worktree`。编排层是 TypeScript（约 3,900 行），
git 部分约 739 行，映射到 `child_process.execFile('git', ...)` 几乎 1:1。

**技术上可行，但环境上不成立**：教室机器大多没装 git ——
这正是当初放弃改造 LiveAgent、另起本项目的原因之一。
（本项目自己的文档 `docs/7gai工具对照与实现规划.md` §2.1 已确认这一点。）

### ❌ 持久记忆（SQLite FTS）

设计很好（Markdown 为准、SQLite 只是可重建的索引；系统提示词冻结 + 用户消息增量注入，
为的是不破坏 prompt 缓存）。

**卡在 `better-sqlite3` 是原生模块**，而本项目的硬约束是
**ABI 110（Electron 22）下禁止引入任何原生模块**。
`node:sqlite` 要 Node 22，主进程是 Node 16。

### ❌ MCP 桥接 / Skills / 定时任务 / 终端 / SSH / SFTP / Gateway

| 功能 | 卡在哪 |
|---|---|
| MCP 原生桥接 | Tauri 侧 Rust 实现；且 MCP server 多为 Node/Go，Win7 上跑不动 |
| Skills（约 5,500 行） | 脚本通过 Bash 执行；且体积与本项目定位不匹配 |
| 定时任务（约 9,000 行） | 需 SQLite + 调度器；`powerMonitor` 在 Electron 22 无 resume 钩子 |
| 终端 / SSH / SFTP | 需 `node-pty`（原生模块）与 SSH 栈 |
| Gateway 远程网关 | Go 服务端，与桌面架构无关 |
| 多模态 / Tunnel / 浏览器扩展 / CUA / TTS | 平台绑定或超出教学场景 |

### ❌ 流式传输层 / 多供应商抽象

**一个反直觉的发现**：LiveAgent 仓库里**根本没有 SSE 解析** ——
streaming、delta 累积、跨供应商工具调用归一化**全部**来自外部 npm 包
`@earendil-works/pi-ai`。仓库里的适配器只有 19~216 行，是薄薄一层供应商怪癖。

所以「移植多供应商支持」实际等于**引入一个第三方依赖**，
而本项目已有一套可用的 SSE + 工具调用累积实现（`ai.ts`）。
不值得换。

### ❌ i18n / Trajectory / 轨迹视图

- **i18n**：参考实现手写 54 行引擎、2,702×2 条翻译。本项目界面是中文单语且自洽，
  引入双语是新增维护面，不是能力提升。
- **Trajectory**（约 7,500 行）：执行轨迹可视化（甘特图、TTFT、缓存命中等）。
  属于诊断/可观测性功能，对本项目的教学场景价值有限，且体积远超收益。
- **FileLedger**（压缩时保留「碰过哪些文件」的确定性清单）：想法好，
  但它是配合完整压缩存储层用的；本项目没移植那层，单独拿过来没有落点。

## 四、验证方式

新增 5 个离线校验脚本，全部接入 `npm run build`（构建前自动跑）：

| 命令 | 覆盖 | 项数 |
|---|---|---|
| `npm run check:editmatch` | Edit 匹配级联 | 16 |
| `npm run check:argguard` | 参数截断守卫 | 13 |
| `npm run check:cmdsafety` | 命令安全三件套 | 30 |
| `npm run check:budget` | 上下文预算与压缩策略 | 44 |
| `npm run check:watch` | 文件监视时序（原有） | — |
| `npm run check:node16` | Node 16 API 边界（原有） | — |

**为什么是独立脚本而不是塞进 smoke**：这些全是纯逻辑，
跑一遍几毫秒，不需要窗口、文件系统或 AI。塞进 smoke 会被窗口的不稳定性拖累
（这一点参考项目的 Rust 单测划分也是同样思路 —— 把测试与 `#[cfg(test)]` 分开）。

### 关于 smoke 在本环境跑不起来

`npm run smoke` 在当前沙箱环境里失败于
`/dev/shm/.org.chromium.Chromium.* 权限不够` —— 这是**环境限制，不是本次改动导致的**：
用 `git stash` 回到未修改的 HEAD 跑，失败信息完全一致。
`typecheck`（主进程 + 渲染层）、`build` 与 5 个离线校验均通过。

## 五、如果继续做，优先级建议

按「收益 ÷ 风险」排序：

1. **压缩存储层**（Segment + Summary Checkpoint）—— 约 5,500 行纯 TS，无平台依赖。
   是参考项目里最大的可移植子系统。但需要想清楚：教学场景真的需要
   自动总结长对话吗？还是「提示开新对话」就够？当前选了后者。
2. **ManagedProcess 式后台任务** —— 文件日志 + 字节游标读取 + 按进程启动时间
   校验 pid（防 pid 复用误杀）。Win32 部分（`OpenProcess`/`taskkill /T /F`）在 Win7 可用。
   本项目的 `jobs.ts` 目前在内存里缓冲输出。
3. **Git worktree 子代理** —— 技术上最完整，但要先解决「教室机器没有 git」。
